ในสัปดาห์นี้ ได้มีการใช้งาน AI เพื่อช่วยเป็นคู่คิด (Pair Programming Assistant) ในการทำความเข้าใจหลักการออกแบบฐานข้อมูลเชิงสัมพันธ์ การเลือกชนิดข้อมูลและกำหนดข้อกำหนดความถูกต้อง (Constraints) ใน SQLite การเขียนคำสั่ง SQL Query ทั้งระดับพื้นฐานและระดับสูง (JOIN, GROUP BY, Aggregate Functions, Indexing) ตลอดจนการทำ Negative Testing เพื่อพิสูจน์ความสมบูรณ์ของฐานข้อมูล โดยมีรายละเอียดการใช้งานดังนี้:

## ครั้งที่ 1: การออกแบบ Schema และการกำหนด Constraint (CP18, CP19, CP23)

**ถามอะไร**
- สอบถามแนวทางการแยกระหว่างตาราง `users` กับ `requests` ว่าควรเลือก Primary Key อย่างไร ทำไม `users.id` ควรเป็น INTEGER แต่ `requests.id` ควรเป็น TEXT และการเขียนคำสั่ง `CHECK` constraint ใน SQLite เพื่อควบคุมค่าประเภทคำร้องและสถานะ
- วิธีการทำให้ไฟล์ `schema.sql` สามารถรันซ้ำได้ (Idempotency) โดยไม่ติดปัญหา Table already exists หรือ Foreign Key ล็อก

**AI ตอบว่าอย่างไร (สรุปสั้น)**
- อธิบายความแตกต่างระหว่าง **Surrogate Key** (`users.id` เป็น INTEGER AUTOINCREMENT เน้นประสิทธิภาพการจัดทำ Index และขนาดพื้นที่จัดเก็บน้อย เหมาะกับ Foreign Key) กับ **Natural / Business Key** (`requests.id` เป็น TEXT ในรูปแบบ 'REQ-XXX' สื่อความหมายชัดเจน มนุษย์จดจำและอ้างอิงง่าย)
- แนะนำการใช้ `CHECK (status IN ('pending', 'in-progress', 'completed'))` และเน้นย้ำให้ใส่ `PRAGMA foreign_keys = ON;` เพราะ SQLite ปิดการตรวจ Foreign Key โดยค่าเริ่มต้น
- อธิบายลำดับการลบตารางด้วย `DROP TABLE IF EXISTS` ว่าต้องลบตารางลูก (`requests`) ก่อนตารางแม่ (`users`) เสมอ เพื่อป้องกันข้อผิดพลาดเรื่อง Foreign Key ชี้ไปยังตารางที่ถูกลบไปแล้ว

**ใช้ส่วนไหน / แก้เองตรงไหน**
- นำคำแนะนำมาสร้างโครงสร้างตารางใน `schema.sql` ให้สมบูรณ์ กำหนดค่าเริ่มต้น (`DEFAULT`) และข้อกำหนด `NOT NULL` ครบทุกคอลัมน์ พร้อมเพิ่มข้อมูลตั้งต้นที่หลากหลายเพียงพอต่อการทดสอบ

## ครั้งที่ 2: การเขียน SQL Query ค้นหาข้อมูลและการประยุกต์ใช้ JOIN (CP22)

**ถามอะไร**
- ขอคำแนะนำการเขียนคำสั่ง SQL Query เพื่อตอบโจทย์ทั้ง 8 ข้อ โดยเฉพาะการดึงข้อมูลข้ามตารางด้วย `JOIN` เพื่อเอาชื่อผู้แจ้งมาแสดงคู่กับคำร้อง
- สอบถามเงื่อนไขการค้นหาคำร้องเร่งด่วนที่ยังไม่เสร็จ และการใช้งาน `LIKE` สำหรับค้นหาคำบางส่วนในรายละเอียด

**AI ตอบว่าอย่างไร (สรุปสั้น)**
- แนะนำรูปแบบการเขียน `INNER JOIN` โดยระบุเงื่อนไขการเชื่อมตารางผ่าน `requests.requester_id = users.id` และการใช้ Alias เช่น `u.name AS requesterName` เพื่อให้ชื่อฟิลด์ตรงกับ Data Model เดิม
- ชี้ให้เห็นว่าเงื่อนไข "คำร้องเร่งด่วนที่ยังไม่เสร็จ" ควรกำหนดเป็น `priority = 'urgent' AND status != 'completed'` เพื่อให้ครอบคลุมทั้งสถานะ `pending` และ `in-progress`
- แนะนำการใช้ `%` หน้าและหลังคำค้นหาใน `LIKE '%ไม่ทำงาน%'` เพื่อให้ค้นพบข้อความไม่ว่าจะอยู่ตำแหน่งใดในรายละเอียด

**ใช้ส่วนไหน / แก้เองตรงไหน**
- เขียนคำสั่ง SQL ทั้ง 8 ข้อลงใน `queries.sql` และทดสอบรันจริงกับฐานข้อมูล `campus.db` ตรวจสอบความถูกต้องของผลลัพธ์ทุกรายการ

## ครั้งที่ 3: การทำ Challenge ขั้นสูง (GROUP BY, LEFT JOIN, CREATE INDEX)

**ถามอะไร**
- สอบถามความแตกต่างระหว่าง `INNER JOIN` กับ `LEFT JOIN` ในกรณีที่ต้องการทำรายงานสรุปจำนวนคำร้องแยกตามผู้ใช้งานทุกคน
- สอบถามหลักการทำงานของ `CREATE INDEX` ว่าควรสร้างบนคอลัมน์ไหน และมีข้อดีข้อเสียอย่างไร

**AI ตอบว่าอย่างไร (สรุปสั้น)**
- อธิบายว่าหากใช้ `INNER JOIN` ผู้ใช้ที่ยังไม่เคยแจ้งคำร้องเลยจะหลุดหายไปจากรายงาน แต่ถ้าใช้ `LEFT JOIN` ร่วมกับ `GROUP BY u.id` และ `COUNT(r.id)` ผู้ใช้ทุกคนจะยังคงปรากฏในรายงานแม้จะมีคำร้องเป็น 0
- เปรียบเทียบ Index เหมือนดัชนีท้ายเล่มหนังสือ ช่วยให้การค้นหาด้วย `WHERE` หรือการเชื่อมโยงด้วย `JOIN` รวดเร็วขึ้นมาก โดยควรสร้างกับคอลัมน์ที่ถูกค้นหรือเชื่อมบ่อยที่สุด ได้แก่ `status` และ `requester_id` พร้อมเตือนว่า Index มีต้นทุนเรื่องพื้นที่จัดเก็บและการเขียนข้อมูลที่ช้าลงเล็กน้อย

**ใช้ส่วนไหน / แก้เองตรงไหน**
- นำคำสั่ง `GROUP BY`, `LEFT JOIN` และ `CREATE INDEX` ไปใส่ใน `queries.sql` และ `schema.sql` พร้อมรันตัวตรวจ `check-week09.mjs` จนผ่าน Challenge ครบ 3/3 รายการ

## ครั้งที่ 4: การทดสอบ Constraint Validation (Negative Testing — CP25)

**ถามอะไร**
- ขอแนวทางในการทำ Negative Testing เพื่อพิสูจน์ว่า Constraint ทั้ง 5 แบบ (Foreign Key, CHECK, UNIQUE email, UNIQUE id, NOT NULL) ทำงานได้จริงและปฏิเสธข้อมูลที่ผิดพลาดตามที่คาดหวัง

**AI ตอบว่าอย่างไร (สรุปสั้น)**
- ให้ตัวอย่างคำสั่ง SQL ที่จงใจละเมิดข้อกำหนดแต่ละข้อ เช่น ใส่ `requester_id` เป็น 99999 (ไม่มีในระบบ), ใส่ค่าสถานะภาษาไทย `'ยกเลิก'`, ใส่อีเมลซ้ำกับสมชาย, ใส่รหัสคำร้องซ้ำ `'REQ-001'`, และส่งค่า `location` เป็น `NULL`
- อธิบายรูปแบบ Error Message ของ SQLite ที่จะเกิดขึ้นเมื่อ Constraint ทำงาน

**ใช้ส่วนไหน / แก้เองตรงไหน**
- นำคำสั่งไปทดสอบรันจริงกับ `campus.db` ตรวจสอบข้อความ Error Message ที่ฐานข้อมูลส่งกลับมา และบันทึกผลการทดสอบลงใน `DATA_MODEL.md` และ `EVIDENCE.md`

## ครั้งที่ 5: การวิเคราะห์เชื่อมโยงผลลัพธ์ SQL กับสถาปัตยกรรมในสัปดาห์ที่ 10 (CP24)

**ถามอะไร**
- ขอแนวคิดการเปรียบเทียบผลลัพธ์ของการทำ `JOIN` ใน SQL กับรูปแบบข้อมูล JSON ที่ REST API ส่งให้ React ในสัปดาห์ที่ 07 เพื่อเตรียมตัวสำหรับสัปดาห์ที่ 10

**AI ตอบว่าอย่างไร (สรุปสั้น)**
- อธิบายหลักการสถาปัตยกรรมแบบแบ่งชั้น (Layered Architecture):
  1. ฐานข้อมูลทำหน้าที่ Normalize เพื่อกำจัดความซ้ำซ้อนของข้อมูล (Data Redundancy)
  2. Service Layer ในสัปดาห์ที่ 10 จะนำคำสั่ง `JOIN` นี้ไปใช้ดึงข้อมูล และแปลงเป็น JSON DTO ที่มีรูปทรงเดียวกับ Week 07
  3. Controller, Route และ React Component ฝั่งหน้าบ้านจึงไม่ต้องแก้ไขอะไรเลย เพราะรูปร่างข้อมูลยังเหมือนเดิม

**ใช้ส่วนไหน / แก้เองตรงไหน**
- นำข้อคิดนี้ไปเขียนวิเคราะห์และเรียบเรียงเป็นภาษาของตนเองในหัวข้อที่ 6 ของ `DATA_MODEL.md`

**เข้าใจโค้ดที่ได้มาไหม** ☑ เข้าใจทั้งหมด ☐ เข้าใจบางส่วน ☐ ยังไม่เข้าใจ

## สรุปภาพรวมการทำงาน

- **ส่วนที่เขียนและวิเคราะห์เองทั้งหมด:**
  - การวิเคราะห์ปัญหา Update Anomaly, Data Redundancy และ Insertion/Deletion Anomaly จากโจทย์จริง
  - การกำหนดรายละเอียดเหตุผลในการเลือกชนิดข้อมูลและ Constraint ของแต่ละคอลัมน์ในตาราง
  - การลงมือรันทดสอบและตรวจสอบผลลัพธ์ของคำสั่ง SQL ทุกข้อด้วยตนเอง
  - การเรียบเรียงเอกสาร `DATA_MODEL.md` และ `EVIDENCE.md` ทั้งหมด
- **ส่วนที่ AI ช่วยเหลือและให้คำแนะนำ:**
  - ชี้แนะแนวทางความแตกต่างระหว่าง Surrogate Key กับ Business Key
  - แนะนำ Best Practice ในการเขียน SQL เช่น การใช้ `LEFT JOIN` สำหรับคนที่ไม่เคยแจ้ง และการใช้ Alias
  - ช่วยตรวจสอบความครอบคลุมของกรณีทดสอบ Negative Testing
  - ให้มุมมองเชิงสถาปัตยกรรมในการเชื่อมโยง Database เข้ากับ Service Layer ของ Week 10
- **สิ่งที่ได้เรียนรู้และพัฒนาทักษะ:**
  - เข้าใจอย่างลึกซึ้งว่าทำไมการ Normalize ฐานข้อมูลเชิงสัมพันธ์จึงคุ้มค่ากว่าการเก็บข้อมูลแบนราบ แม้จะต้องแลกมาด้วยการเขียนคำสั่ง `JOIN`
  - เข้าใจบทบาทของ Database Constraint ว่าเป็น Defense in Depth ที่สำคัญที่สุดในการรักษาความสมบูรณ์ของข้อมูล (Data Integrity)
