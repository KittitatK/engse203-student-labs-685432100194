## ครั้งที่ 1: การศึกษาความปลอดภัยและการทดสอบ SQL Injection (CP31)

**ถามอะไร**
- สอบถามหลักการทำงานของคำสั่ง `curl` ในการทดสอบเจาะระบบ SQL Injection ว่าต้องรันที่ไหนและคำสั่งมีความหมายอย่างไร
- ทำไมการใช้ `?` (Parameterized Query) ถึงสามารถป้องกันการโจมตีได้ แม้ว่าผู้โจมตีจะใส่ `' OR '1'='1` หรือ `; DROP TABLE`
- ทำไมคำสั่ง `ORDER BY` ถึงใช้เครื่องหมาย `?` แทนชื่อคอลัมน์ไม่ได้ และมีวิธีการป้องกันอย่างไร

**AI ตอบว่าอย่างไร (สรุปสั้น)**
- `curl` เป็นคำสั่งสำหรับยิง HTTP Request ผ่าน Terminal โดยตรงในขณะที่เซิร์ฟเวอร์ Express กำลังเปิดรันอยู่ (บน Windows แนะนำให้ใช้ `curl.exe` เพื่อป้องกันปัญหาการตีความ String ของ PowerShell)
- Parameterized Queries จะแยกขั้นตอน Compile ไวยากรณ์ SQL ออกจากขั้นตอน Binding ข้อมูลอย่างเด็ดขาด ทำให้ค่าที่ส่งมาถูกมองเป็นข้อความธรรมดา (String Literal) เสมอ ไม่สามารถหลุดออกมารันเป็นคำสั่ง SQL ได้
- ตัว `?` ถูกออกแบบมาเพื่อผูกกับ Value ของข้อมูลเท่านั้น ไม่สามารถใช้แทนโครงสร้างฐานข้อมูล (Identifier) เช่น ชื่อคอลัมน์หรือชื่อตารางได้ ทางแก้ไขคือการใช้ **Allowlist** ตรวจสอบคอลัมน์ที่อนุญาตก่อนนำไปประกอบคำสั่ง SQL

**ใช้ส่วนไหน / แก้เองตรงไหน**
- นำคำสั่ง `curl.exe` ทั้ง 3 รูปแบบไปยิงทดสอบจริงบน Terminal และนำผลลัพธ์ `[]` (0 รายการ) ไปบันทึกใน [SECURITY_TEST.md](file:///e:/engse203-student-labs-685432100194/labs/week-10/source/SECURITY_TEST.md) และ [API_CONTRACT.md](file:///e:/engse203-student-labs-685432100194/labs/week-10/source/API_CONTRACT.md)

## ครั้งที่ 2: การจัดการ Error จากฐานข้อมูลและการแปลงเป็น AppError (CP32)

**ถามอะไร**
- ตรวจสอบว่าทำไมในไฟล์ `requestService.js` ถึงยังไม่ผ่านเกณฑ์จริงของ CP32 แม้ว่าตัวตรวจ `check-week10.mjs` จะขึ้นเครื่องหมายผ่าน
- ขอคำแนะนำการแปลงข้อความ Constraint Error ของ SQLite (FOREIGN KEY, CHECK, UNIQUE) ให้เป็น HTTP Status ที่ถูกต้อง (400 และ 409) พร้อมข้อความภาษาคนที่เข้าใจง่าย

**AI ตอบว่าอย่างไร (สรุปสั้น)**
- ตัวสคริปต์ตรวจเพียงว่ามีไฟล์ `errorHandler.js` หรือไม่ แต่ในเนื้องานจริงของ `requestService.js` หากเกิด Database Constraint ข้อมูลจะพ่น Error ออกมาเป็น **500 Internal Server Error** ซึ่งผิดหลักการ เพราะความผิดพลาดเกิดจากผู้ใช้ส่งข้อมูลไม่ถูกต้อง ไม่ใช่ระบบล่ม
- แนะนำการสร้างฟังก์ชัน `toAppError(err)` ใน `requestService.js` เพื่อดักจับ Error Message และโยน `AppError` ที่มี status 400 (สำหรับ FOREIGN KEY / CHECK) และ 409 (สำหรับ UNIQUE) พร้อมห่อฟังก์ชัน `create()` และ `updateStatus()` ด้วย `try...catch`

**ใช้ส่วนไหน / แก้เองตรงไหน**
- Import `AppError` จาก `../middleware/errorHandler.js` และเขียนฟังก์ชัน `toAppError()` รวมถึงห่อคำสั่ง `INSERT` และ `UPDATE` ใน Service ด้วยตนเอง

## ครั้งที่ 3: การเขียนชุดทดสอบอัตโนมัติด้วย Supertest (CP33)

**ถามอะไร**
- ขอแนวทางการใช้งาน Supertest ในการเขียน Integration Test อย่างน้อย 6 เคสที่ยิงเข้าฐานข้อมูลจริง
- สอบถามโครงสร้างคำสั่งและการส่งข้อมูลแบบ GET, POST, PUT, DELETE และการตรวจเช็ค Response Body กับ Status Code ด้วย Node.js Test Runner (`node:test` และ `node:assert/strict`)
- ทำอย่างไรไม่ให้ข้อมูลที่เกิดจากการทดสอบ POST ไปตกค้างสะสมอยู่ในฐานข้อมูลจริง

**AI ตอบว่าอย่างไร (สรุปสั้น)**
- Supertest ช่วยจำลองการยิง HTTP Request เข้า Express App โดยตรงโดยไม่ต้องเปิดเซิร์ฟเวอร์จริง
- แนะนำชุดการทดสอบทั้ง 6 เคส ครอบคลุม: การดึงข้อมูลทั้งหมด, การแปลงชื่อผู้แจ้งด้วย `JOIN`, การดึงตาม id (200/404), การสร้างคำร้อง (201), การกรองข้อมูลไม่ครบ (400), และการยิง SQL Injection แล้วไม่หลุด
- แก้ปัญหาข้อมูลค้างในฐานข้อมูล โดยหลังคำสั่ง `POST` สำเร็จ ให้สั่ง `DELETE /api/requests/:id` ลบข้อมูลที่เพิ่งสร้างออกทันทีในเทสเคสเดียวกัน ทำให้สามารถรัน `npm test` ซ้ำกี่รอบก็ยังผ่านได้อย่างสม่ำเสมอ

**ใช้ส่วนไหน / แก้เองตรงไหน**
- นำโค้ดชุดทดสอบทั้ง 6 เคสไปใส่ใน [api.test.js](file:///e:/engse203-student-labs-685432100194/labs/week-10/source/api/tests/api.test.js) และรันคำสั่ง `npm test` ตรวจสอบผลลัพธ์ผ่านครบ 6/6 เคส

## ครั้งที่ 4: การอัปเดตเอกสารข้อตกลง Data Model และ API Contract (CP34)

**ถามอะไร**
- หัวข้อที่ต้องเพิ่มใน `API_CONTRACT.md` สำหรับสัปดาห์ที่ 10 มีอะไรบ้าง
- ทำไมโครงสร้างในตารางฐานข้อมูลถึงไม่ตรงกับ JSON Response ที่ API ส่งออก
- พฤติกรรมสำคัญของ `POST /api/requests` ที่ต้องระบุใน Contract คืออะไร

**AI ตอบว่าอย่างไร (สรุปสั้น)**
- ต้องเพิ่มหัวข้อ Data Model โครงสร้างตาราง `users` และ `requests` พร้อมระบุ Constraints
- ในฐานข้อมูลเก็บ `requester_id` เป็นตัวเลขเพื่อทำ Normalization ป้องกันข้อมูลซ้ำซ้อน แต่ API ส่งออกเป็น `requesterName` เพราะฝั่ง Frontend ต้องการนำไปแสดงผลทันที เลเยอร์ Service จึงต้องทำหน้าที่เป็นตัวแปลงด้วย `JOIN` และ `AS`
- พฤติกรรมสำคัญของ `POST` คือ: หากส่งชื่อ `requesterName` ที่ยังไม่มีในระบบ Service จะทำ Auto-create ผู้ใช้ใหม่ให้อัตโนมัติ ซึ่งเป็นพฤติกรรมที่นักพัฒนาภายนอกไม่สามารถคาดเดาได้จากการดูเฉพาะ Endpoint จึงจำเป็นต้องบันทึกไว้ใน Contract อย่างชัดเจน

**ใช้ส่วนไหน / แก้เองตรงไหน**
- นำรายละเอียด Schema, คำอธิบายความแตกต่างของโครงสร้าง, พฤติกรรม Auto-create User, และผลการทดสอบ SQL Injection ไปปรับปรุงใน [API_CONTRACT.md](file:///e:/engse203-student-labs-685432100194/labs/week-10/source/API_CONTRACT.md) พร้อมปรับเวอร์ชันเอกสารเป็น 2.1.0
